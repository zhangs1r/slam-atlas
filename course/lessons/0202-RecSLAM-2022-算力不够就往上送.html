0. 开课即纠正：把「仿真」这件事说清楚

导览课 0199 立过一句口号：看位置之前，先看清这篇到底是什么。上一课 0201 兑现过一次（它是综述、不是系统论文），这一课要兑现第二次，而且这一次是一个字符造成的误读。

一、「仿真」这个词是从哪来的

有一份清单把这一篇标成「边缘计算加速多机器人仿真」。这个说法是错的，而错的源头很小：语料库里的文件名被截断了。

它的真实一级标题是：

Edge Robotics: Edge-Computing-Accelerated Multirobot Simultaneous Localization and Mapping

这句话在说什么：这不是一个「仿真平台」的名字，这是一句完整的工作陈述——「同时定位与建图」，也就是 SLAM 的全称。而语料库里的文件名是 2022_Edge_Robotics__Edge-Computing-Accelerated_Multirobot_Sim.md，那个 _Sim 是被 66 字符长度限制切掉之后剩下的残骸：它正好切在 Simultaneous 的第三个字母上。于是 Simultaneous 变成了 Sim，Sim 又被顺理成章地读成了 simulation。

这不是这一篇独有的问题。本季这三篇应用论文的文件名尾部全部被切过：自主飞行那篇切在 ..._Semantic_SL.md、运动规划那篇切在 ..._navigation_.md、这一篇切在 ..._Multirobot_Sim.md。所以在语料库里按清单给的名字去找文件是找不到的，只能按前缀匹配——这件事本身值得记住：文件名的截断是一种系统性失真，不是个别事故。

二、而且它不只是仿真：它有真机原型

就算把 _Sim 读对了，还有第二个坑：会以为它「只做仿真」。不是。这一篇是真机 ＋ 仿真双验证的系统论文：真机部分用了 3 台 TurtleBot3 加 1 台边缘服务器（边缘侧是 Jetson TX2），机器人侧的算力模块是一块 Raspberry Pi，车顶装 RPLIDAR A1 做激光扫描；仿真部分则是 Gazebo 里的公寓场景（主场景 13×18 m²，配 3 台边缘服务器），另外还有 4×4 m² 对称场景与 5×5 m² 非对称场景。真机测试场是自建的会议室，约 6×5.5 m²。

两种验证的份量也不一样：规模与调度实验跑在仿真里（机器人规模从 10 台一路到 50 台），可行性证明跑在真机上（论文把真机那组叫 proof-of-concept，概念验证）。所以这一课真正该讲的重点是卸载粒度、层次融合、调度算法——而不是「仿真怎么加速」。

互动判断

文件名 2022_Edge_Robotics__..._Multirobot_Sim.md 里的 _Sim 是什么？

1. 它在系统链的哪一环

把上一课 0201 立的那条七环链搬出来——传感器 → 感知/前端 → SLAM/里程计 → 地图 → 规划 → 控制 → 执行器——然后问一句：这一篇占哪几格？

答案是两格：第三格（SLAM/里程计）和第四格（地图）。但这里有一个很要紧的状语：它改的是这两格的「算力部署与融合方式」，不是这两格的算法。换句话说，它没有发明任何新的 SLAM，也没有发明任何新的地图融合数学——它做的是把「SLAM 计算跑在哪台机器上」和「多张地图在哪一层合并」这两件事重新安排了一遍。

那它到底交出了什么、又没碰什么？原文自己的界定很清楚：「我们对 SLAM 计算整体封装成一个函数模块来处理机器人原始数据」——这句话是全篇的立场声明。它不改进 SLAM 前端、不做回环检测、不做语义；它不做机器人自主性，机器人端只保留轻量的采集与打包。它也不解决多机 SLAM 的算法问题——地图一致性、回环、通信受限，这三样在多机 SLAM 里是老大难，而这一篇一个都不碰。

那它在地图上画的是哪一笔？原文 Related Work 里给了一句自评：CCM-SLAM、EdgeSLAM、Edge-SLAM 这些已有工作要么只做单机器人、要么忽略多边缘的情况，而 RecSLAM 是首个用边缘计算优化多机器人激光 SLAM 的工作。这句话的分量要放在第八季那个语境里才看得出来：第八季多机协同块解决的是「多个机器人怎么一起把一张地图做对」，而这一篇解决的是「多个机器人加一台 SLAM，怎么在算力与通信上跑得动」。一个是算法问题，一个是基础设施问题。

2. 它要解决什么：传统云方案的两个瓶颈

要理解一篇系统论文，最好的入口是看它先量了谁的问题。这一篇的第二节做了一件很实在的事：把当时最主流的方案——「机器人各自跑 SLAM、把局部地图通过广域网传上云、云端合并」——拿来做了一遍实测，然后把两个瓶颈摆出来。

瓶颈一：机器人被自己的 SLAM 压死

原文监听了机器人在跑 SLAM 时的 CPU 负载：最低 83.60%、平均 93.82%，有时直接顶到 100.00%。注意这是「最低」就有 83.60%，也就是这台机器人在整段任务里几乎没有喘气的空隙。一台机器人如果在跑 SLAM 时 CPU 已经打满，那它就没有余量再做任何别的事情——避障、通信、异常处理都挤不进去。

瓶颈二：通信时延又大又不稳

第二个瓶颈在链路这一侧。原文实测的传统云方案总时延是：WiFi 下 3.83 s，5G 下反而涨到 5.36 s。这两个数字放在一起很有意思——换了更快的网络，时延反而变大了，原文的解读是这段时延的波动主要来自通信侧，而广域网的通信时延本身就不受你控制。这正是摘要里那句话的来源：实测表明数据卸载的通信开销使它难以实际部署。

把两个瓶颈合起来看，就得到了这一篇的问题定义：主流云方案的瓶颈同时出现在「机器人的算力」和「机器人的通信」两侧，而它要做的，是把这两侧的压力同时降下来。

⚠️ 精读时发现的原文疑点（引用时请留意）

这一篇的正文里有几处数字与单位对不上。精读阶段已逐条核实，这里如实列出，不要照抄错的那一个：

  • 上传时延的单位印错了。原文把上传时延写成 3.13, 2.35, and 1.88 ms（4G / 5G / WiFi）。毫秒不成立：1.88 ms 不可能成为总时延 3.83 s 的主要部分，也无法与紧邻的 1.51 s 本地计算相加凑到 3.83 s。按数量级应为秒——1.88 s 加 1.51 s 约 3.39 s，再加云端合并约 3.83 s，才自洽。
  • 百分比口径不自洽。原文称本地计算 1.51 s 占 WiFi 总时延的 49.74%，但 1.51 除以 3.83 等于 39.4%；要得到 49.74%，分母应约为 3.04 s。这两个数至少有一个与它标注的口径不符，引用时请只取一个并注明口径。
  • 通道名前后不一致。一处说联系云有三条通道 3G, 4G, and WiFi，后面报的数据却是 4G、5G、WiFi——3G 出现后消失、5G 未经介绍就出现。
  • 角速度的单位错了。一处把角速度写成 0.20–0.80 m/s²，角速度单位不可能含 m/s²，应为 rad/s 或度每秒。
  • 一句话里混了两个指标。原文有一句写「相对贪心策略平均降低 58.71%、最高降低 12.16%」——平均值大于上限，逻辑不可能。结合上下文，58.71% 来自算法运行开销那张图、12.16% 来自执行时延那张图，不可当作单一加速比引用。
  • 扫描域的形状前后矛盾。一处说机器人扫描域「用圆表示（因为能 360 度扫描）」，而正文某张图的图注说扫描域「抽象为扇形（sector）」。

另外，原文 Algorithm 3 第 2 行的下标印成了 $i \in \mathcal{E}$，但那一行里被遍历、被移除的变量其实是边缘服务器，且同一行的左端已经用了 $j$；按正文的英文描述（pick an edge server $j$ such that…）下标应为 $j \in \mathcal{E}$，属笔误。

3. 四段时延：边缘计算不是白赚的

这一节是全课的枢纽。要讲清「把计算送出去」到底赚了什么、又付出了什么，原文给了一个很好用的最小模型：把从「数据产生」到「地图可用」的整段时间，拆成四段。先用一张图把它摆出来。

现在把这个模型写成公式。原文用工整的三段式把端到端时延拆了下来。

$$t_r = t_r^{\mathrm{pack}} + t_{r\to e}^{\mathrm{trans}} + t_e^{\mathrm{frame}}$$

这句话在说什么：一台机器人拿到「自己那张机器人地图」要等三件事：打包（把原始激光帧和 IMU 数据装成可以发出去的样子）、上传（从机器人 $r$ 传到它所属的边缘服务器 $e$）、边缘上做一次坐标变换（把数据对齐到统一的坐标框架里）。它为什么这么算：因为在这个设计里机器人已经不计算地图了，所以「算地图」那一段被从机器人身上彻底摘掉了，留下的是采集与搬运动作。

$$t_e = \max_{r\in e} t_r + t_e^{\mathrm{fuse}}$$

这句话在说什么：一台边缘服务器要等它名下最慢的那台机器人把数据送到，才能开始融合。它为什么这么算：因为融合需要所有输入齐了才能做，这就是为什么后面要专门做「负载均衡」：只要有一台机器人拖后腿，整个边缘节点就跟着慢。$\max$ 这个符号是整篇调度算法的根源。

$$t_c = \max_{e}\left(t_e + t_{e\to c}^{\mathrm{trans}}\right) + t_c^{\mathrm{fuse}}$$

这句话在说什么：同理，云端也要等最慢的那条边缘支路，然后才能做全局融合。它为什么这么算：$t_c$ 就是这一篇要压的唯一目标——从原始数据采集到全局地图完成的端到端总时延。于是整篇的优化目标可以写成一句话：

$$\min\ t_c \quad \mathrm{s.t.}\ (2),(3)$$

这句话在说什么：全篇所有的调度算法，只为压缩这一件事——最慢那条支路的总时间。净赚多少：原文报的最终结果是相对当时最先进的云方案最高降低 39.31% 的处理时延；分机器人规模看是 6 台机器人 39.31%、8 台 26.50%、10 台 12.96%。同时机器人侧的 CPU 平均负载从 93.82% 降到 53.91%（最低 36.18%）。这两个数字一个是「快了多少」，一个是「轻了多少」，要一起看才完整：只快不轻，说明只是把压力挪走了；既快又轻，才说明账算得过来。

互动判断

把 SLAM 计算从机器人卸到边缘服务器之后，机器人身上发生的直接变化是什么？

4. 三级融合链：机器人只传原始帧

上一节讲了「算被送到了边缘」，这一节要讲一个更隐蔽、也更有意思的设计：机器人往外送的，到底是一张「算好的地图」，还是「没算过的原始帧」？

直觉上你会觉得应该送地图——地图已经压缩过了，肯定比原始帧小。但这一篇选的是送原始帧。原因是原文自己给的：SLAM 计算本质上是紧耦合的，强行把它拆开会导致复杂度爆炸。那就干脆不拆：把整个 SLAM 当作一个黑盒整体搬到边缘去。代价是往上游多传了数据，收益是上游那一步完全不用改算法。然后它在下游把账找回来——在边缘先合并一次，去掉重叠冗余，往云上传的数据量就小了。这是一个「往上游多传、往下游少传」的净收益论证。

5. 调度：两个子问题

架构定了，剩下的就是一个纯排班问题：哪几台机器人分给哪台边缘服务器？原文把它拆成两个子问题，各配一个算法。

子问题一：均衡分组

它要同时满足两个目标，而这两个目标的方向还不太一样：

  • 组内机器人数量要尽量均衡。因为地图融合要做两两匹配，$k$ 张图就是 $k(k-1)/2$ 次检查，复杂度是二次的——把太多机器人塞给一台边缘服务器会拖垮整体完成时间，原文叫它「长尾效应」。这是「数量」这个维度。
  • 组内重叠度要尽量大。因为重叠度越高，融合后剩下的冗余越少，边缘地图越小、上传越省。原文测过：两个等大小的输入在重叠度 50%（即完全重合）时，融合出的边缘地图就等于其中一张输入的大小；重叠度越高，融合后体积越小。这是「体积」这个维度。

原文为此先建了一张重叠图：每个顶点是一台机器人的地图，两个顶点之间有边就表示这两张地图有重叠，边的权重就是重叠度（没重叠就不连边）。然后在这张图上做两件事：

$$\mathrm{gain}(\nu) = \sum_{u\in P_i} w(u,\nu) - \sum_{u\in C\backslash\{\nu\}} w(u,\nu)$$

这句话在说什么：把候选顶点 $\nu$ 拉进第 $i$ 组，能增加多少组内重叠、减少多少组间重叠，这个差值就是它的「收益」。它为什么这么算：因为组内越重叠、融合后体积越小；组间越不重叠，说明冗余都被关在组里没有漏出去。第一项越大越好、第二项越小越好，所以用减法把两者捏成一个可比较的数。

$$f\!\left(\langle P_1,P_2,\dots,P_N\rangle\right) = \sum_{u\in P_i,\ \nu\in P_j,\ i\neq j} w(u,\nu)$$

这句话在说什么：这是「跨组的加权边总和」，也就是所有被留在组与组之间的重叠量。越小越好——越小说明重叠都被收进组里了。它为什么这么算：把它当成打分函数之后，分组问题就变成一个可以拿来搜索的目标：Tabu 搜索（原文 Algorithm 2）就是不停地交换不同组里的顶点，让这个值一路降下去。

子问题二：资源感知卸载

$$j \leftarrow \arg\min_{j\in\mathcal{E}}\left(L_j(P_i) + \frac{\mathcal{D}(P_i)}{B_j}\right)$$

这句话在说什么：给第 $i$ 组挑一台边缘服务器 $j$：把「这一组在 $j$ 上的计算时延预测 $L_j(P_i)$」和「这一组的输出数据量除以 $j$ 到云的带宽」加起来，谁的和小就选谁。它为什么这么算：因为端到端时延里同时包含计算和传输两部分，一台算力强但带宽窄的服务器，可能还不如一台算力中等但带宽宽的。选完就把这台服务器从候选列表里移除，是一对一的贪心匹配。净赚多少：两层调度的开销都很小——原文报10 台机器人时调度耗时不到 1 ms，50 台机器人时 36 ms，而复杂度分别是 $O(V+L)$（$V$ 顶点、$L$ 边）与 $O(N)$（$N$ 为组数）。也就是说调度本身可以放心地在线跑，它并不是瓶颈。

还有一个实现层面的细节值得记下来：重叠度矩阵是周期性算出来的，用的工具是一个基于 ROS multirobot_map_merge 改造的包。这意味着调度器的输入不是实时精确值，而是周期性估计值——原文承认这依赖「重叠面积估计误差在可容忍范围内」这个假设，并说明由于机器人数较少、估计误差可以接受。换句话说：这套调度在小规模时误差可控，规模一大就未必。

另外，原文自己列的局限里还有两条值得记住：它的调度是集中式的（实现上选一台边缘服务器当协调者，负责收集信息、估重叠度、跑调度算法），以及机器人到边缘的链路被假定稳定（同一局域网内）。真实的链路抖动与失败被列为未来工作，可能要靠多接入移动边缘计算做部分卸载。

6. onboard 还是 offboard：与 0200 的正面冲突

现在把两课并排放在一起看，你会看到一个非常干净的对立。0200 那篇 Falcon 4 说：算力不够？那就把算力往机上堆。它换了 i7-10710U，坚持全部计算 onboard，连地面站都不要，理由是它在密林树冠下飞，链路本来就不可靠。而这一篇说：算力不够？那就把计算往机外送。机器人端只剩一块 Raspberry Pi，SLAM 全部搬到边缘服务器上，理由同样硬：机器人 CPU 已经打满到 93.82%。

7. 它是横向的基础设施轴

这一节要回答本季的核心问题：把它放回前十季的坐标里，它到底添了什么新东西？

先说它没有添什么。多机器人 SLAM 有三件老大难：地图一致性（几台机器人各自建的地图怎么保证能对齐）、回环（跨机器人的回环怎么检测与优化）、通信受限（带宽不够时怎么取舍）。这三件事第八季多机协同块（0168 起）都正面处理过，而这一篇一个都不碰——它把「多机器人 ＋ SLAM」整体打包，当成一份可以被切分、被分配、被调度的算力负载。

它添的是另一条轴：机器人 → 边缘 → 云。这条轴和 A 到 J 季一直在讲的那条「算法纵向轴」是正交的。

对比项 A 到 J 季的算法纵向轴 这一篇引入的基础设施横向轴
问的问题这个算法怎么算得更准、更快、更鲁棒？这些计算跑在哪台机器上、哪一层合？
改的东西模型、损失、前端后端、优化策略卸载粒度、融合层级、调度策略
SLAM 的地位是被改进的对象是一个黑盒函数，一行不改整体搬运（GMapping）
成功的判据精度、鲁棒性、轨迹误差端到端时延、CPU 负载、调度开销
前十季覆盖过吗主干七季都在讲这条轴没有。这是前十季从未出现过的一环

为什么要强调「正交」？因为这两条轴可以互相独立地组合。你完全可以把一套新的 SLAM 算法（纵向轴上的进步）装进 RecSLAM 的框架里，让它在边缘上跑——这正是原文自己承认的边界：它的 SLAM 内核只验证了 GMapping，语义与视觉 SLAM 都没涉及。反过来说，一个算法再准，如果机器人的 CPU 打满到 93.82%，它在真机上就跑不出应有的表现。这就是「基础设施轴」的分量：它不决定你能算得多好，它决定你算不算得动。

8. 和前面课程怎么接

接哪一段 怎么接
第八季多机协同块（0168 起）「多机器人」这个题目同源，但处理的问题完全不同：第八季问「多台机器人怎么把一张地图做对」（一致性、回环、通信受限），这一篇问「多台机器人加一台 SLAM 怎么跑得动」。读完第八季再看这一篇，最该带走的一句是：算法对了不等于跑得动。
第四季激光主干（0073 起）它用的 SLAM 内核是现成的 GMapping，也就是第四季讲过的激光 SLAM 经典实现。「算法零改动」这句话的分量就在这里：第四季里那些前端匹配、栅格建图、粒子滤波，在这一篇里一行都没变，变的只是它跑在哪个 CPU 上。
本季 0200（自主飞行）正面冲突，务必并读。0200 把算力往机上堆（i7-10710U、全部 onboard、无地面站），0202 把算力往机外送（Raspberry Pi 采集、SLAM 搬到边缘）。两条路的代价完全不同：一个赌链路不可靠，一个赌链路可靠。
本季 0201（运动规划综述）0201 给了一张七环链当坐标系，并且强调「感知的输入不一定来自机器人自己身上的传感器」。这一篇把这个说法推到了极致：连计算都可以不在机器人身上。
本季 0203（下一课）下一课回到「SLAM/里程计这一环本身」——Wildcat 是一套真正的激光惯性 SLAM，它和这一篇正好构成一对：一篇讲这一环里的算法怎么做，一篇讲这一环的计算该放哪。
本季导览 0199导览课预告的两处纠正，这一课落实了第一处（「仿真」是误读）。「看位置之前，先看清这篇到底是什么」这句话，在这里有了一个极端的例证：一个字读错，整课讲歪。

最后补一句这一篇自己的位置声明。它把「机器人只传原始帧」这个决定解释得很清楚：因为 SLAM 计算本质上是紧耦合的，强行拆分会导致复杂度爆炸。所以它宁可往上游多传一点、在下游靠融合去重找回来。这是一次很典型的工程权衡：不去动那个最复杂的东西，而是在它周围重新排布数据流。

9. 读完你应该能回答

合上这一课之前，先自己回答下面五个问题。答不上来的，回去看对应的小节。

① 这篇到底是什么？

它是一篇真机 ＋ 仿真双验证的系统论文，标题里的 Simultaneous Localization and Mapping 就是 SLAM 全称。清单里的「仿真」是文件名 66 字符截断造成的误读。

② 它在链的哪一环？

只碰第 ③ 环（SLAM/里程计）与第 ④ 环（地图），而且改的是这两环的「跑在哪、怎么合」，不是算法。上游是机器人传感器原始帧，下游是云端全局地图。

③ 四段时延是什么？

打包 pack → 传输 trans → 计算 compute → 融合 fuse。卸载让机器人侧的 compute 从 1.51 s 缩到几乎为零，代价是 trans 段变长。边缘计算是用传输换算力。

④ 它赚到了什么？

端到端时延最高降 39.31%（6/8/10 台机器人分别是 39.31/26.50/12.96%）；机器人 CPU 平均负载从 93.82% 降到 53.91%；调度本身很轻（10 台不到 1 ms、50 台 36 ms）。

⑤ onboard 还是 offboard？

「算力不够」有两条方向相反的解法：0200 往机上堆（赌链路不可靠），0202 往机外送（赌链路可靠）。这是场景判断，不是技术偏好。

课后练习

  1. 为什么说这一篇「不是一篇 SLAM 论文」？请从它的输入输出、以及它和 SLAM 内核的关系两方面说明。
    展开查看答案
    三方面：① 输入是机器人传感器的原始帧（LaserScan 的时间戳与测距、以及做坐标变换用的 IMU），不是任何中间表示；② 输出是云端全局地图，交给云端下游应用（原文举例是导航与家具设计），它自己不消费这张地图；③ 它用的 SLAM 内核是现成的 GMapping，原文原话是「我们对 SLAM 计算整体封装成一个函数模块来处理机器人原始数据」——算法零改动：它不改进前端后端、不做回环检测、不做语义。所以它论文的主体是架构（机器人、边缘、云三层）加两个调度算法，而不是任何 SLAM 算法。
  2. 用四段时延（pack / trans / compute / fuse）解释：为什么说「边缘计算不是白赚的，它是用传输换算力」？
    展开查看答案
    因为卸载只做了一次搬移：把 compute 段从机器人的时间轴搬到边缘服务器的时间轴上。机器人侧原本要付的 1.51 s 本地 SLAM 计算几乎消失，但代价是每一帧原始数据都要往外传，所以 trans 段明显变长。整个系统的端到端时延能不能降，取决于「省下的计算时间」是否大于「多付的传输时间」——原文实测的结果是能降，最高降低 39.31%（6 台机器人时）。这也解释了为什么这一篇要费那么大力气做调度：它必须把传输这一侧的代价压到最小，这笔交换才划算。另外要注意，原文的三段式（机器人侧、边缘侧、云侧）里都有 max 算子：任何一条支路上有一台机器或一台服务器拖后腿，整体时延就被它卡住，这正是负载均衡存在的理由。
  3. 为什么 RecSLAM 宁可传「原始帧」也不传「算好的地图」？请说明理由，并指出它用什么办法把因此增加的通信负担补回来。
    展开查看答案
    理由：原文说 SLAM 计算本质上是紧耦合的，强行拆开会导致复杂度爆炸。所以它不拆——把整个 SLAM 当作黑盒整体搬到边缘，代价是上游多传了数据，收益是上游一步算法都不用改（对多机器人来说，这还意味着不要求各机器人跑同样的算法）。补回来的办法：在下游做一次准备性融合（preparative fusion）——边缘服务器先把它名下多台机器人的地图合并、去掉重叠冗余，得到体积更小的边缘地图，再上传到云。原文还给了定量依据：两个等大小的输入在重叠度 50%（完全重合）时，融合结果就等于其中一张输入的大小，重叠度越高、融合后越小。所以它是一个「往上游多传、往下游少传」的净收益论证，也解释了为什么分组算法要追求「组内重叠度尽量大」。
  4. 把这一篇和 0200 并读：「算力不够」这件事有哪两条相反的解法？各自押注在什么前提上？
    展开查看答案
    两条解法：① 往机上堆——0200 换了 i7-10710U，坚持全部计算 onboard、连地面站都不要；② 往机外送——0202 让机器人只留一块 Raspberry Pi 做采集与打包，SLAM 全部搬到边缘。两者面对的是同一个问题（机器人算力不足），但方向相反。各自的前提：0200 押的是「链路不可靠」——它在密林树冠下飞，长期任务里任何对外依赖都是风险，所以它宁可付机重、功耗与散热成本；0202 押的是「链路可靠」——它把机器人放在同一个局域网的公寓里、一个机器人固定连一台边缘服务器，原文也承认真实部署中链路可能抖动甚至失败，把这件事列为未来工作。所以选哪条不是技术品味问题，而是先回答「我的链路靠不靠得住」。
  5. 这一篇引入的「机器人到边缘到云」这条轴，和前十季的「算法纵向轴」是什么关系？为什么说它正交？
    展开查看答案
    关系：正交——两条轴可以互相独立地组合。纵向轴问的是「这个算法怎么算得更准、更快、更鲁棒」，改的是模型、损失、前后端与优化策略；横向轴问的是「这些计算跑在哪台机器上、地图在哪一层合」，改的是卸载粒度、融合层级与调度策略。正交的证据有两条：① 你可以把一套新的 SLAM 算法装进 RecSLAM 的框架里让它在边缘跑——原文自己承认它的 SLAM 内核只验证了 GMapping，语义与视觉 SLAM 都没涉及，这正好说明框架与算法是可分离的；② 反过来说，一个算法再准，如果机器人 CPU 打满到 93.82%，它在真机上一样跑不出应有的表现。所以这一篇的分量在于：它不决定你能算得多好，它决定你算不算得动。而这也是本季「看位置」的另一层含义——不仅要看 SLAM 在链上占哪一格，还要看这一格的计算放在哪。

最后留一句这一篇自己划出的边界：它的 SLAM 内核只验证了 GMapping，它不解决多机 SLAM 的算法问题，它的调度是集中式的，它的链路被假定稳定。这四条边界并不削弱它的价值——恰恰相反，正因为把边界划得这么清楚，「首个用边缘计算优化多机器人激光 SLAM」这句话才站得住。
