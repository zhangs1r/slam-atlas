DeepFactors（2020）：学习先验进因子图

上一节证明了「把深度压成一串数就能优化它」，但那个系统自己承认：不实时、不回环、不泛化。这一节看同一批人怎么把三件事一次补齐——做法是给学习先验找一个标准的概率后端 🧩

1. 上一节差在哪：三条短板，三条补丁

这是本节最有价值的一段，因为它把「学术论文之间的接力」摊开给你看了。原文在相关工作里对 CodeSLAM 的批评写得很不客气，一共三条：

短板一：不是一个完整的 SLAM

原文：「lacked features of full SLAM」——它只有滑动窗口的建图/视觉里程计，没有回环、没有重定位

短板二：做不到实时

原文：「not capable of real-time performance」——那一大块 1 秒级的雅可比计算，就是拦路虎

短板三：不泛化到真实手持场景

原文：「did not generalise to real handheld camera scenes」——训练数据是渲染出来的合成场景

于是 DeepFactors 的补法也很清楚（原文 §II 逐个对应）：加上局部与全局回环、加重定位；把整张地图一起做批优化（不再是固定窗口）；优化 GPU 使用、重做实现；以及一个战略性的选择——用标准因子图软件（GTSAM）来搭后端。

最后这一点值得多说一句。原文说，用标准框架带来的好处是「straightforward probabilistic integration of different sensor modalities which was not possible with the previous formulations of dense SLAM」——从此稠密 SLAM 也能像稀疏 SLAM 一样，方便地把 IMU、GNSS 等新传感器作为新的因子加进图里。这不是一个实现细节，而是一个架构上的解锁：稠密 SLAM 从此有了和稀疏 SLAM 同等规格的后端。

另外原文还顺手澄清了它与另外两篇的关系，这对我们把第三季串成线很有用：

vs CNN-SLAM（0054）

「an example of other directly comparable work」，原文把 CNN-SLAM 选为主要的定量对比基线，因为它也是「whole estimated trajectory、不用真值位姿」来评测重建的少数系统

vs BA-Net

BA-Net 也用了类似 CodeSLAM 的「基深度图 + BA」思路，而且端到端训练过（可能学出更适合 SfM 的表示）。但它不是实时 SLAM、不维护一致的多关键帧地图

vs DeepTAM

DeepTAM 把 DTAM 的 TV-L1 优化与跟踪都换成网络，效果超过经典方法；但它沿用「跟踪/建图分开」的老结构，且做不到实时。原文还点出它的软肋：仍然依赖网络见过所有输入变化

原文对自己的定位（这句话很值得记）

原文强调自己的方法「relies less on the network generalisation」，理由是后续优化能修正网络的坏预测——「in our system, neural networks are mainly used for obtaining an image conditioned manifold to optimise over」。

这句话是整条「学习 + 优化」路线的题眼：网络的职责从「给出答案」降级成「给出一个可搜索的曲面」。网络犯错不再是灾难，只是初值差一点。

2. 三种因子：各管一件事

这是本节的技术主干。DeepFactors 把「两个视角之间应该自洽」这件事拆成了三种不同的度量方式，它们各自擅长不同的东西。

2.1 光度因子（photometric）：比灰度

第一项是稠密 SLAM 的老朋友（式 2、3）：

$$e_{pho}^{ij} = \sum_{\mathbf{x}\in\Omega_i}\big\|\,\mathtt{I}_i(\mathbf{x}) - \mathtt{I}_j(\omega_{ji}(\mathbf{x},\mathbf{c}_i,\mathtt{I}_i))\,\big\|^2$$

读法：把 $i$ 帧的某个像素按深度投影到 $j$ 帧上，两个像素的灰度应该差不多。这里 $\omega_{ji}$ 是那个「投影用的 warp 函数」，而它需要深度——而深度来自 code。所以光度因子的梯度会一路传到 code 上去，这就是「深度能被优化」的通道。

⚠️ 一个容易写错的地方

式 2 里没有出现任何鲁棒核，就是一个平方和。请不要想当然地给它补一个 Huber——三个因子里只有后两个用了鲁棒核，而且用的还不是同一个。这正是本文值得细看的地方。

2.2 重投影因子（reprojection）：比特征点的像素位置

第二项借用经典 SfM 的间接法（式 4）：匹配到的特征点，它「投影过去的位置」应该和「实际观测到的位置」一致。原文明确用了 Cauchy 鲁棒核，理由是它「has a constant response to outliers」——对离群点给出恒定（而不是继续增长）的代价。特征用的是 BRISK。

2.3 稀疏几何因子（sparse geometric）：比深度

第三项是这篇的特色（式 5）：把 $i$ 帧的深度投影到 $j$ 帧，得到的深度应该和 $j$ 帧自己的深度一致。原文在这里用的是 Huber 范数，而且为了省算力，只在一组均匀稀疏采样的像素上求值，并且特意说明可以每次迭代换一批像素，从而对整张图做随机优化。

2.4 消融实验：谁管轨迹、谁管重建

既然有三种因子，自然会问：「能不能只用一种？」原文在 ScanNet 验证集的三个场景上做了消融（Table I，`pho` 是基线，另外两种单独加和一起加）：

正确深度 pc110：69.14% → 71.05% → 71.81% → 73.66%

scene0606_02（重建提升最明显）

原文从这张表里读出的结论很干净：加上任一种因子都能降低轨迹误差、提升重建精度；其中重投影因子对「轨迹」影响更强，几何因子对「重建」影响更强；三个一起用效果最好。至于机制，原文给了两句解释：重投影项因为显式地做了特征匹配，所以「improves local minima avoidance and increases convergence rate」；而几何项则引入了「世界上只有一张表面」这个先验，把各帧独立的深度图在缺乏光度信息的无纹理区域「钉」成一份重建。

3. 一个小装置：one-way frames（单向帧）

这是我认为本节最「巧」的一个设计，值得单独讲。

问题出在「只用相邻关键帧」这个设定上。光度误差要发挥作用，最好同时有小基线和大基线的配对——小基线好对齐、大基线给深度信息。但如果只把当前关键帧与「最后 N 个关键帧」相连，这个条件不一定满足。

原文的解法是引入一类特殊的帧：它们不携带深度、不被优化，只负责把信息喂给最新的关键帧。原文的定义是「one-way frames that do not have attached depth and are used to feed information to refine the latest keyframe」。等优化若干步之后，这些帧就被边缘化掉、从图里删除。

4. 学习先验怎么进概率框架

这一节回答的是标题里的问题：「学习先验进因子图」到底怎么进去的。

4.1 一句话：把深度写成 code 的线性函数（式 1）

$$\mathrm{D}_i = f(\mathbf{c}_i, \mathtt{I}_i) = \mathrm{D}_i^0 + \mathbf{J}(\mathtt{I}_i)\,\mathbf{c}_i$$

其中 $\mathrm{D}_i^0 = f(\mathbf{0}, \mathtt{I}_i)$ 是「全零 code」解码出来的深度，$\mathbf{J}(\mathtt{I}_i) = \partial \mathrm{D}_i/\partial \mathbf{c}_i$ 是那个只依赖图像的雅可比。原文给出的理由是：「为避免优化过程中代价高昂的重新线性化，我们要求这个关系是线性的」（式 1 上方原话）。

这个式子的意义在第 1 节里已经点过：它把「一张深度图」变成了「一个 32 维参数生成的流形上的一点」。于是优化不再是「在三十万维空间里瞎跑」，而是「在这个学出来的、有结构的低维曲面上滑动」。

4.2 一个关键数字：code size = 32

这是本节与上一节最直观的对照，也是本模块最值得停下来想一想的地方：

上图的右边那半个结论，原文有明确的依据：「code size 32 …… This is the maximum code size that we can achieve real-time results with in our SLAM system.」——注意这句话的措辞：不是「32 够用」，而是「32 是实时的上限」。这是一个非常诚实、也非常工程化的表述。

互动判断

上一节的 CodeSLAM 说 code size 在 128 处精度饱和（再大收益极少），而这一节的 DeepFactors 却只用了 32 维。最准确的解释是哪个？

4.3 还有一个「初始化」的小改进

上一节说 CodeSLAM 用「全零 code」当默认初始化。DeepFactors 发现这在真实相机上不够好，于是额外加了一个编码器，直接从图像预测一个 code（原文 Fig. 5 显示这样比零 code 初始化更好）。它同时说明，为了让预测的 code 落在与学到的 code 相同的空间里，对这个预测也施加了同样的潜在损失。

4.4 还有一件必须做的事：把 code 拉住

因为训练时通过变分损失让 code 流形「靠近零均值高斯」，所以在优化过程中必须用 zero-code 先验因子（zero-code prior）把它正则化住，否则优化可能把 code 推到流形之外——那样解码出来的深度就不可信了。这就是「学习先验进概率框架」的具体形态：先验不是一句口号，而是一个实实在在挂在图上的因子。

另外原文还明确指出一个实现约束：由于因子是为「单向 warp」设计的，一对关键帧之间需要加两个因子才能同时优化两者的 code/深度。

5. 实时是靠什么换来的

这一节把「实时」这件事拆开看，因为它的答案里有一条非常值得记住的教训。

5.1 四个来源

① 低维 code（32）

直接压低优化变量的数量

② 线性解码器 → 雅可比可预计算

延续上一节的取舍：让 $\mathbf{J}$ 只依赖图像，每关键帧算一次

③ iSAM2 增量求解

原文把批 MAP 问题的求解交给 iSAM2：它「stores a factorisation of the batch Jacobian in the form of a Bayes Tree」，新增变量时只对受影响的因子重新线性化与重分解，因此能在探索型运动下做到近常数时间更新

④ GPU / CPU 分工 + 跟踪与建图交替

稠密 warp、优化、跟踪交给 GPU（CUDA）；重投影与稀疏几何因子在 CPU 上算；同时让跟踪与建图步骤交替执行，以跟上不断到来的图像

5.2 一个必须讲清的数字：340 ms 里只有 16 ms 是网络

这是本节我最想让你记住的一个数字，因为它打破了一个常见直觉——「用了神经网络所以慢」。

原文在性能一节给出：每初始化一个新关键帧，需要约 340 ms，其中只有 16 ms 花在网络前向传播上，其余全部花在用 tf.gradients 计算雅可比上。原文对这个现象的解释很坦诚：这是「backward-mode auto-differentiation based implementation」的低效所致——那套实现是为「标量函数的梯度」优化的（机器学习的常见需求），而这里需要的是「每个输出像素对潜在表示（code）的导数」，于是不得不在网络上跑大量遍。

原文的预测：这个 340 ms 里有巨大的优化空间

原文明确写下：「This time can be drastically reduced with engineering effort and we predict it should be possible to reduce the overall time required to run the network to around 30 ms.」

请注意这个比例：340 ms → 预计 30 ms，是把「网络相关的开销」压掉约 90%。这条说明了一个在深度学习 + 机器人里反复出现的教训：真正的瓶颈往往不在模型本身，而在你「向模型要梯度」的方式。这个坑，任何把网络嵌进优化器的人都会遇到。

跟踪速度则是另一回事：原文报告当前帧与最新关键帧的跟踪约 250 Hz——因为跟踪只做 SE(3) 的全图 Lucas-Kanade（原文用的就是这个名字：standard direct whole-image SE3 Lucas-Kanade），不涉及网络。

5.3 一个「性能随场景切换」的实用结论

原文还说明了一个很有意思的取舍：系统的整体性能「varies greatly」取决于四个因素——关键帧之间的连接数量、启用了哪些因子、iSAM2 里被重新线性化的因子数量、以及是否发生回环。因此作者给出了两条使用建议：

探索型运动

相机快速移动时，只开光度 + 重投影因子，先把速度保住。原文原话：通常是「we typically limit our system to only use the photometric and reprojection error to allow it to keep up with the fast camera movement」

局部重建（桌面 AR / 房间尺度）

运动不那么激进时，可以打开几何因子换取更好的重建质量

这种「按场景切换因子」的设计，在写论文时是个软肋（不够「一劳永逸」），但在工程上非常实在。

5.4 一个细节：回环为什么只加重投影因子

原文在回环一节写了一句很值得琢磨的话：因为光度误差的收敛域（convergence basin）通常更小，所以在闭合一个全局回环时，只加重投影因子。

把这句话讲成白话：全局回环意味着「两个关键帧的位姿初值可能差得挺远」。光度误差要生效，需要初值已经把两张图对齐得差不多（因为它是逐像素比灰度的，差一点就完全对不上）；而重投影误差基于特征点匹配，对「差得远」更宽容。所以在这种「初值不好」的场合，用重投影因子更稳妥。

这条与现代 SLAM 系统的普遍做法一致，也呼应了第二季 0019 讲过的「不同残差有不同的吸引域」这件事。

Table III 的说明里写着：CNN-SLAM 是在「关闭位姿图优化」的情况下跑的，而本文是在「关闭回环」的情况下跑的；另外「in order to limit computation we have disabled the geometric factor for the evaluation」（为限制计算量，评测时关闭了几何因子）。原文还说明 room 与 plant 两个序列被剔除了，因为它们含大量丢帧、可能歪曲结果。

请记住这个细节的意义：当你在论文里看到一张「我们赢了」的表格时，值得花三十秒去找它的脚注。这篇论文把口径都写出来了，这是值得肯定的做法；但读者仍要知道，这个对比并不是「双方都开到最强」的对比。

6.4 该讲清的代价

平坦纹理墙表达不了

这是最硬的一条局限，而且原文自己指名道姓地报告了：tum/seq2 输给 CNN-SLAM，原因是 32 维 code「typically not able to represent fully flat depth easily」。「更大的 code 更能表达」与「更小的 code 更能实时」在这里正面撞上了。

单目仍需「最优尺度」

评测时用了 benchmark 脚本算出的最优尺度来缩放。也就是说：它没有从根上解决单目尺度问题——这一点与我们第一条暗线上的其他方法一致，最终还是要靠 IMU 或双目（这正是后面 VIO 模块要讲的事）。

探索型运动必须牺牲几何因子

如 5.3 所述，快速运动时只能开光度 + 重投影，几何因子得关掉。这意味着存在一个"运动速度—重建质量"的取舍曲线。

雅可比计算的实现效率

340 ms 里 324 ms 花在求雅可比上。原文自己也把「更快地获得网络雅可比」与「更好的几何因子 GPU 实现」列为未来工作。

本节小结：这个模块给出了一个「分工模板」

把这个模块三节课连起来看，你会看到一条很清晰的思路演化：

0054 CNN-SLAM：网络给出深度 → 只用不确定度把它融合进来（网络是「外部输入」）。
0055 CodeSLAM：网络给出一个可优化的低维流形 → 深度成为可求导的变量（网络是「参数化工具」）。
0056 DeepFactors：同一个流形装进标准的概率因子图 → 稠密 SLAM 拿到了和稀疏 SLAM 同等规格的后端（网络是「先验提供者」）。

原文对最后这一步的意义说得很明确：用标准框架让「不同传感器模态的概率融合」成为可能，而这在过去的稠密 SLAM 公式里做不到。用一句话概括这三节的分工模板：让网络负责「提供先验」，让概率推断负责「一致性与不确定性」，让因子图负责「可扩展与可组合」。

这条路线也会在后面阶段继续长出来——第一季 0015 讲过的 3D 高斯泼溅，走的正是「可微渲染 + 梯度优化」这条同源的路。

7. 巩固练习

课后练习

  1. CodeSLAM 有三条短板，本节分别怎么补的？请逐条对应写出。
    展开查看答案

    ① 「不是一个完整 SLAM」（缺回环与重定位）→ 加了局部与全局回环检测与闭合，以及重定位（跟踪丢失时对全部关键帧做低分辨率对齐）；② 「不实时」→ 把 code 降到 32 维、用线性解码器让雅可比可预计算、用 iSAM2 做增量求解、GPU/CPU 分工并让跟踪与建图交替；③ 「不泛化到真实手持场景」→ 改用真实的 ScanNet 数据（约 140 万张图）训练，并用真实序列做评测，同时明确承认平坦纹理墙上是弱点。

  2. 三种因子里，哪一种「对轨迹影响更强」、哪一种「对重建影响更强」？原文是怎么解释这两个不同作用的？
    展开查看答案

    重投影因子对轨迹影响更强，几何因子对重建影响更强。

    原文的解释是：重投影项因为显式地用到了特征匹配（BRISK），所以能「improve local minima avoidance and increases convergence rate」，从而给系统增加鲁棒性；而几何项引入的是「世界上只观测到一张表面」这个先验，它把各帧独立的深度图「pins together to form a single reconstruction」，特别在缺乏光度信息的无纹理区域起关键作用。三个一起用效果最好。

  3. 为什么在闭合全局回环时只加重投影因子，而不加光度因子？
    展开查看答案

    原文的理由是光度误差的收敛域（convergence basin）通常更小。全局回环意味着两个关键帧之间的位姿初值偏差可能较大；光度误差是逐像素比较灰度的，需要在图像已经大致对齐的前提下才有梯度可循，初值差得多就很容易掉进错误的局部极小。而重投影误差建立在特征点匹配之上，对初值偏差更宽容。因此在这种「初值不好」的场合，用重投影因子更稳。

  4. 原文报告初始化一个关键帧要 340 ms，其中只有 16 ms 是网络前向。剩下的时间花在哪？作者预计能压到多少？这说明什么？
    展开查看答案

    剩下约 324 ms 花在用 tf.gradients 计算雅可比上——因为需要求「每个输出像素对潜在 code 的导数」，而 backward-mode 自动微分的实现是为「标量函数梯度」优化的，于是不得不在网络上跑很多遍。原文预计通过工程努力可以把整体网络相关时间压到约 30 ms。

    说明两件事：第一，把网络嵌入优化器时，真正的瓶颈常常不是模型推理，而是「向模型要梯度」的方式；第二，一个「看起来很慢」的深度学习系统，可能只是实现没调好——340 ms 里 95% 是可以优化掉的开销（当然这仍是作者的预测，不是已实现的结果）。

  5. 为什么 deep factors 要把 code 从 128 降到 32？这是「退步」吗？代价体现在哪里？
    展开查看答案

    不是退步，而是目标函数变了。CodeSLAM 报告 128 处精度饱和，那是在「以重建精度为主要目标」下的最优；DeepFactors 引入实时约束后，原文明确说 32 是「the maximum code size that we can achieve real-time results with」——是实时上限，不是精度最优。

    代价在实验里就能看到：在 tum/seq2（fr3_nostructure_texture_near_withloop）这个相机对着平坦纹理墙的序列上，本文只拿到 16.92% 的正确深度，输给 CNN-SLAM 的 24.08%。原文归因就是「code 太小，难以表示完全平坦的深度」。这提醒我们：任何「压缩表示」都有它表达不了的东西，而那个东西会在特定场景里变成失败模式。

  6. 本节为什么强调「用标准因子图软件（GTSAM）」是一个重要选择？它对「稠密 SLAM」这个领域意味着什么？
    展开查看答案

    原文说这带来了「straightforward probabilistic integration of different sensor modalities which was not possible with the previous formulations of dense SLAM」。

    含义是：过去的稠密 SLAM 为了速度，通常自己做一套简化的、位姿与地图交替优化的流程，很难把新传感器（IMU、GNSS 等）作为标准因子加进去。改用标准因子图后，稠密 SLAM 的后端规格就与稀疏 SLAM 对齐了——只要把新观测写成一个因子挂上去即可。这也是原文自我定位里「a unified SLAM framework」的一部分：让稠密/稀疏、学习/模型这两对曾经对立的路线，在同一套概率框架里共存。
