1. 一句话结论，外加一个必须先澄清的作者问题

先给结论：Faster-LIO 把 FAST-LIO2 地图里那棵 ikd-Tree 换掉了，换成了一种叫 iVox（incremental voxels，增量式体素）的稀疏哈希结构。换完之后，查询不需要再顺着树一层层往下走，而是「一算就知道在哪个格子」；同时因为没有了指针追逐，各个格子的计算可以分给多个 CPU 核心同时干。原文的实验结论是：在保持同等精度的前提下，比 FAST-LIO2 快 1.5 到 2 倍。

先澄清一个容易被转述错的细节：作者里没有 Cui

有些网络转述会把作者写成「Bai, Cui, Chen 等」。我们的精读材料核对过原文，正确的作者列表是：Chunge Bai、Tao Xiao、Yajie Chen、Haoqian Wang、Fang Zhang、Xiang Gao，来自香港大学 MaRS 实验室——与 FAST-LIO、FAST-LIO2 同门。名单里没有 Cui。本节以原文作者列表为准。

2. 它针对 FAST-LIO2 的哪个环节动刀

上一节结束时，ikd-Tree 看起来已经很强了：插入 $O(\log n)$、查询 $O(\log n)$、没有 nanoflann 那种尖峰。那还能从哪儿再快？

原文先给了 ikd-Tree 一个公道的评价，然后立刻转身：

「FastLIO and FastLIO2 are LIO systems that achieve almost 100 Hz in large-scale scenarios. The incremental k-d tree significantly reduces the tree update time, which is also verified in our experiments. … Nevertheless, we show that iVox is even faster than the ik-d tree in FastLIO2 while accomplishing the same level of accuracy.」
（中译：FastLIO 与 FastLIO2 在大规模场景中达到接近 100 Hz。增量 k-d 树显著降低了树的更新时间，这一点在我们的实验中也得到了验证。…… 尽管如此，我们要说明：iVox 比 FastLIO2 中的 ik-d 树更快，同时达到同等精度。）

那么 Faster-LIO 具体嫌弃树的哪一点？原文摘要第一段把答案说得很干脆：

「To achieve the high tracking speed, we neither use complicated tree-based structures to divide the spatial point cloud nor the strict k nearest neighbor (k-NN) queries to compute the point matching.」
（中译：为了达到高跟踪速度，我们既不用复杂的树状结构来划分空间点云，也不用严格的 k 最近邻（k-NN）查询来计算点匹配。）

这句话里其实藏了两把刀，要分开看：

第一把刀：砍掉「树」

树结构有个天生的毛病——查询必须沿着指针从根一路走到叶：先比一个坐标，决定往左还是往右；再比一个，再决定一次……就像进一个陌生小区，一路问人「三号楼往哪走」。这一路走下来没法跳步，而且因为路径是串行依赖的（不走到这一层就不知道下一层去哪），很难分给多个 CPU 核心同时跑。

第二把刀：放弃「严格」近邻

原文明确承认 iVox 的 k-NN「is easy, effective, but not strict compared with tree-like algorithms」（比树状算法简单、有效，但不严格）——它是近似的。这是一个主动的取舍：与其花大力气找「绝对最近的那个点」，不如快速找「足够近的若干点」，反正后面拟合平面也不需要绝对精确。

原文还给了一句很有说服力的动机，讲的是为什么「快」本身就有价值：

「For many real robots or vehicles, LIO is not the only algorithm running in the system. All the active modules must share the computation resource. The system would be more robust if we had a faster and more lightweight LIO.」
（中译：对许多真实的机器人或车辆来说，LIO 并不是系统里唯一在跑的算法，所有活跃模块都要瓜分算力。如果我们的 LIO 更快、更轻，整个系统就会更鲁棒。）

这句话值得单独记住：在真实系统里，「快」不是炫技，而是把算力还给别的模块。同一台车上可能还有避障、规划、感知在抢 CPU；你的 LIO 省下来的每毫秒，都是别人的。

3. iVox 是什么：切块、哈希、每格限量

iVox 全称 incremental voxels（增量式体素）。它的机制可以用三句话讲完：

① 空间切成体素

把整个世界按固定边长 $s$ 切成一个个小立方格（voxel）。一个点属于哪个格子，只由它的坐标决定。

② 用哈希表定位

体素坐标不是直接当数组下标用（那会浪费巨量内存），而是经过一个哈希函数映射到哈希表的一个槽位。这样即使世界很大，也只给「真的有点的格子」分配空间。

③ 每格只留固定数量的点

每个格子里的点数是有限的（插入时做了下采样），所以「在格子里找最近邻」这件事的代价是可控的小常数，而不是「格子里堆了多少算多少」。

哈希函数原文写得很具体：

$$id_v = \text{hash}(\mathbf{v}) = \left(v_x n_x\right)\ \mathrm{xor}\ \left(v_y n_y\right)\ \mathrm{xor}\ \left(v_z n_z\right)\ \bmod N$$

其中 $\mathbf{v} = \frac{1}{s}\left[p_x, p_y, p_z\right]^{\top}$ 是点 $\mathbf{p}$ 的体素坐标；$s$ 是体素边长，$n_x, n_y, n_z$ 是三个大素数，$N$ 是哈希表的容量。三个坐标各乘一个大素数再逐位异或，是为了把「$x$ 变一点」和「$y$ 变一点」的影响混开，避免不同的三维格子被挤进同一个槽位。

接下来是查询。原文把 k-NN 搜索拆成了三步：

  1. 算出查询点 $\mathbf{p}$ 所在的体素，再找出它周围的邻近体素（原文实现里用的是 6、18 或 26 邻格，见图 Fig. 3）；
  2. 在每一个候选体素里，最多取 K 个近邻；
  3. 把各个体素里的结果合并，挑出最好的 K 个。

为什么只找「周围一圈」就够？因为 k-NN 本来就是有搜索半径限制的：真正有资格当邻居的点，物理上就住在附近的那几个格子。原文的措辞是「The k-NN search is limited within a pre-defined range」（k-NN 搜索被限制在一个预先定义的范围之内）。这也就是前面说的「不严格」——它可能有遗漏，但对 LIO 来说够用。

删除的策略和树完全不同。原文直说「遍历整个体素哈希表太贵了」，所以它不用「按空间位置主动删」，而是用 LRU 缓存（least recently used，最近最少使用）按时间维度淘汰：维护一个「最近访问过的体素」队列并设定最大容量，一旦体素总数超限，就从队尾淘汰最久没用的那些。原文的理由是，哈希表上的插入和删除都是 $O(1)$，「very computationally cheap for real-time LIO algorithms」（对实时 LIO 算法而言计算上非常便宜）。

另外，为了让「每格只留固定数量」真的成立，插入时还有一道过滤：如果邻域里已经有点比这个新点更靠近体素中心，那这个新点就不插了。原文举的经验值是体素边长取 0.5 m 在大多数数据集上表现良好。

4. 同一个招式，三个战场：iVox vs Voxel Hashing vs Instant NGP

「用哈希表把三维坐标变成一个可以直接寻址的索引」——这个招式你在这门课里其实已经见过两次了，只是每次的战场不同。原文自己也点出了它的思想来源：

「For general spatial data storage, voxel hashing is also a common approach to replacing hierarchical tree-like structures. [35] employs hashed voxels for map management in visual SLAM systems and [36] uses voxel hashing for volumetric 3D reconstruction. Furthermore, this letter shows that the hashed voxels can be used for nearest neighbor searching and incremental mapping for LIO systems.」
（中译：对于通用的空间数据存储而言，体素哈希也是替代层次化树状结构的常见手段。[35] 把哈希体素用于视觉 SLAM 系统的地图管理，[36] 把体素哈希用于体积式三维重建。而本 letter 进一步说明，哈希体素还可以用于 LIO 系统的最近邻搜索与增量建图。）

把三次出场并排放在一起：

出场 战场 哈希体素用来干什么 每个格子里装什么
第二季 0034
Voxel Hashing		 稠密表面重建 把空间切成体素块，哈希到显存里，解决「重建的空间无限大、显存有限」的矛盾 TSDF 截断符号距离场
第三季 0038
Instant NGP		 神经辐射场（NeRF） 用多分辨率哈希编码把连续坐标映射成特征向量，喂给一个小网络 可学习的特征向量

Faster-LIO		 激光惯性里程计 把很稀疏的激光点按体素哈希组织起来，支持增量插入与近似 k-NN 查询 原始激光点（每格限量）

一句话总结这个招式：用哈希函数把「三维坐标」直接变成「一个内存地址」，从而绕开所有树形结构必然带来的「一层层找」。

但请注意一个关键的不同：前两次战场上，格子里的东西是「稠密的、连续的场」（TSDF 值、特征向量），而激光点云是极端稀疏的——一帧点云撒在空间里，绝大多数格子里什么都没有。原文特意强调了这一点：「Since the lidar point cloud is sparse, we are not using any volumetric representations like TSDF but a sparse hash map that only stores those voxels having at least one point.」——正因为激光点云稀疏，我们不用 TSDF 那类体积表示，而是一个只存「至少有一个点」的体素的稀疏哈希表。

所以三者的共同点是「哈希 + 体素」这个招式，区别在于格子里装什么、以及格子有多满。同一个招式，三个战场，三种内容物。

5. 优势：定位不再随地图变大，而且天生能并行

5.1 复杂度到底省在哪：一个很容易被说错的点

很多介绍会说「iVox 把 kNN 从 $O(\log n)$ 降到了 $O(1)$」。这个说法方向是对的，但必须精确，否则容易误解。原文对复杂度的讨论讲得非常清楚，而且专门写了一句话来解释它和树方法的区别：

「Please note that the complexity discussed here is defined by the number of points within each voxel, not the whole point cloud. Usually, tree-like methods tend to discuss the search complexity of the whole cloud since the tree is built on it. However, for voxel-based methods, the number of all the points does not directly affect the search efficiency since the voxel index can be calculated in constant complexity.」
（中译：请注意，这里讨论的复杂度是由每个体素内部的点数定义的，而不是整片点云。树状方法通常讨论整片点云上的搜索复杂度，因为树是建在整片点云上的。然而对基于体素的方法而言，总点数并不直接影响搜索效率，因为体素索引可以在常数复杂度内算出来。）

这段话是本节的理论核心。把它拆成三层：

第一层：定位是 $O(1)$

「我在第几格」是一次除法加取整，跟地图里有十万个点还是一亿个点完全无关。这就是哈希相对树最本质的胜利。

第二层：格内搜索的 $n$ 变小了

原文给的格内复杂度是：linear iVox 为 $O(n)$，iVox-PHC 为 $O(\log n)$——但这里的 $n$ 是格子内部的点数，不是全图点数！而格子内部因为做了下采样，$n$ 本来就很小。

第三层：地图变大不再拖慢查询

树的查询随「全图点数」按 $\log n$ 缓慢增长；体素的查询只取决于「身边那一圈的格子有多满」。地图长得再大，也和你这一次查询没关系。这就是它在大规模长序列上优势更明显的原因。

原文还顺便解释了一个 iVox 的设计约束：既然每格只留有限个点，「格内点数」就不会失控，所以 linear 和 PHC 两种内部结构在实际中差别不大——「we will prevent inserting too many points into the same voxel at the incremental mapping step in LIO, so it would not make much difference」。

5.2 并行：为什么这在今天是一个硬指标

第二个优势是天然可并行。前面说过，树的查询是一条串行的指针路径——不走到上一层就不知道下一层去哪，所以很难把一次查询拆给多个核心。而体素的查询没有这种依赖：每一个格子的搜索都是独立的，26 个邻格可以同时开 26 个线程去搜。

原文的实现细节值得抄下来：Faster-LIO 是在 FAST-LIO2 的代码基础上改的，其中一项改动就是「we use libtbb and C++ 17 for parallelization instead of the omp in FastLIO2」（我们用 libtbb 和 C++17 做并行，替代 FastLIO2 里的 OpenMP）。它把整条点云处理管线并行化，包括近邻搜索与 Hessian 的累积。

原文甚至直接提醒读者：由于实现里有大量 CPU 并行计算，核心数、线程数和睿频会主导算法的整体性能——「the number of cores, threads, and boost frequency will dominate the algorithm's overall performance」。它的实验跑在三台机器上：AMD R7-5800X（8 核 3.8 GHz）、Intel Xeon Gold 5128（16 核 2.3 GHz）、以及一台笔记本电脑的 Intel i7-10750H（6 核，睿频 5 GHz）。

大白话：过去我们说「这个算法快」，问的是「它需要几步」；现在这个问题不够了，还要问「这几步能不能同时干」。在多核时代，「能并行」本身就是性能。

6. 把「上千 Hz」这个口径说清楚

这一节要格外小心，因为「上千 Hz」是这类论文最容易被转述夸大的地方。我们只按原文写。

原文里「Hz」出现在三处，措辞略有差别，我们逐条照抄：

出处 原文原话 中译
摘要 「the speed of iVox reaches 1000–2000 Hz per scan in solid-state lidars and over 200 Hz for 32 lines spinning lidars」 iVox 的速度在固态激光上达到每帧 1000–2000 Hz，对 32 线旋转式激光超过 200 Hz
贡献列表 「reaches the speed of over 1500 Hz for solid-state lidar and over 200 Hz for spinning lidar data」 对固态激光数据达到超过 1500 Hz，对旋转式激光数据超过 200 Hz
结论 「achieves over 1000 Hz for solid-state lidars and over 200 Hz for spinning lidars」 固态激光超过 1000 Hz，旋转式激光超过 200 Hz

三处数字不完全一致（1000–2000 / 1500 / 1000 ），这说明它们是不同口径或不同实验条件下的表述。这件事本身要照实说，不要挑一个最大的来用。

（OCR 说明：原文 PDF 抽取出的摘要文本把此处写成了「the speed ofiVox」，是「of」与「iVox」之间丢了空格，我们按原意补回空格，未改动任何数字。）

6.1 它到底是什么，不是什么

它是：整套流程的「处理帧率」

也就是每秒能把多少帧激光扫描走完整条 LIO 流程（含近邻搜索、残差计算、iEKF 更新）。原文在多处把 Hz 和 FPS 换着用——比如实验部分的标题就是「The efficiency of LIO is evaluated by computing the average processing time of each step and the average frames per second (FPS)」。所以这是一个吞吐率指标。

它不是：位姿输出频率，也不是雷达点频

它不是「里程计以 1000 Hz 输出位姿」——真正的位姿输出率受 IMU 频率与扫描结构约束，这一点要看下一节 Point-LIO 才能讲（它才把带宽明确推到 4–8 kHz）。它也不是「激光雷达每秒吐 1000 个点」——固态雷达的点云密度是另一回事。把这两件事混进来，就是夸大。

为什么这个「吞吐率」能那么高？因为它测的是数据处理能力的天花板，而不是真实数据流的速率。传感器实际给多少帧，系统就处理多少帧；iVox 只是说明「这个数据结构自己不吃力」，能把余量留给系统里别的模块——正好呼应第 2 节那句「所有活跃模块都要瓜分算力」。

6.2 与 FAST-LIO2 的真实对比

原文给的对比结论很干脆：

  • FPS 快 1.5 到 2 倍：「Faster-LIO typically achieves 1.5 to 2 times FPS compared with the original FastLIO2, both in solid-state lidar and spinning lidar datasets.」
  • 在旋转式数据上收益更大：「In the spinning lidar datasets (NCLT and UTBM), iVox can save almost 40% to 75% processing time in IEKF, and the overall FPS can be increased by 200% to 320%.」——在 NCLT 与 UTBM 这类旋转式数据上，iVox 能在 IEKF 环节省下约 40% 到 75% 的时间，整体 FPS 提升 200% 到 320%。
  • 在固态数据上收益没那么明显：原文也承认，「in the AVIA dataset, the number of scanned points in solid-state lidar is not so stable as the spinning lidar, the computation time of the iVox is generally shorter than ik-d tree, but not that obvious in sequences like AVIA1 or AVIA2」——固态激光的每帧点数不如旋转式稳定，iVox 通常比 ikd-Tree 快，但在 AVIA1、AVIA2 这类序列上优势不那么明显。
  • 精度保持在同一水平：漂移量级可比（原文口径是「keeping the same level of accuracy」）。

请注意最后两条的诚实度：原文并没有说「在所有场景都快 1.5–2 倍」，它明确指出了收益在不同数据上是不均匀的。这种自我限定恰恰是读论文时最该盯住的地方。

7. 局限：三条原文自己说的边界

Faster-LIO 没有专门的 limitations 小节，但它把几条边界散在了正文里，而且说得很实在。我们把它归成三条。

① 近邻是「不严格」的

原文亲口承认：iVox 的 k-NN「is easy, effective, but not strict compared with tree-like algorithms, yet sufficient for LIO applications」——比树状算法不严格，但对 LIO 应用足够。所以它是一个「用一点精度换速度」的取舍。如果你真的需要精确最近邻，它就不合适。

② 分辨率是个敏感的旋钮

体素边长 $s$ 同时决定三件事：格子太大会丢细节、太小则格子数量和哈希冲突都暴涨。原文说「The leaf size of the filter is the key parameter that tunes the trade-off between accuracy and speed」，并给出经验值 0.5 m。

③ 哈希冲突

不同的三维格子经过哈希后可能落到同一个槽位。原文没有把它当作重点问题（因为哈希桶结构能容纳），但它是这条路线固有的结构性问题——这一点在第一季 0011 讲过的哈希表类方法里也出现过。

原文对第 ② 条给了一张很有说明力的召回率实验，措辞也相当坦诚：

「The recall experiment shows that iVox is faster in low recall rate scenarios, where the parameters are adjusted as small voxel size or small nearby ranges. However, if we want to know the exact neighbors, iVox may not be a good choice since we need a large voxel size or nearby search range to achieve a higher recall rate.」
（中译：召回率实验显示，iVox 在低召回率场景下更快——那对应着小体素边长或小邻域范围。然而，如果我们想要精确的邻居，iVox 可能不是一个好选择，因为要达到更高的召回率就需要更大的体素或更大的搜索范围。）

把这句话翻译成直白的话：iVox 是一条「快 → 准」的曲线，你自己选一个点站上去；它没有免费的午餐，也不是在所有位置上都比树好。

还有一件必须交代的事：Faster-LIO 没有处理「退化场景」。上一节 FAST-LIO2 明确承认，在完全退化的环境（正对开阔海面、天空、纯地面、单一墙面、距墙不足 1 m）会失败。Faster-LIO 换掉的是地图数据结构，并没有换掉观测模型，所以这条边界原封不动地继承了下来。换数据结构解决的是「算得快不快」，解决不了「算不算得出来」。这一点非常值得记牢——它是本季后面几篇论文各自出招的分界线。

8. 收束：本模块三篇的数据结构演进

把 0083、0084、0085 三篇的「地图怎么管」放在一张表里，这一模块的脉络就一目了然：

维度 静态 k-d 树（0083 FAST-LIO、0074 LOAM） ikd-Tree（0084 FAST-LIO2） iVox（本节 Faster-LIO）
插入 整体重建 $O(n\log n)$ 增量 $O(\log n)$（路径插入 + 树上下采样） linear $O(1)$ / PHC $O(\log n)$
删除 不支持，靠重建 懒惰删除 + box-wise + 重建时物理清除 LRU 缓存按时间淘汰
查询（kNN） $O(\log n)$（$n$＝全图点数），树大时慢 $O(\log n)$（$n$＝全图点数），有包围盒剪枝 定位 $O(1)$；格内 $O(n)$ 或 $O(\log n)$（$n$＝格内点数）
并行性 差 双线程并行重建（operation logger） 天然并行（libtbb / C++17）
内存布局 指针树节点 树节点（叶与内部节点都存点） 哈希表 + 体素数组（连续）
适合 离线 / 小地图 实时 LIO、地图随车移动 密集高频扫描、想榨干多核

一句话收束这个模块：FAST-LIO 用一个新的卡尔曼增益公式把「求逆」变小，解决了「算得动」；FAST-LIO2 用直接法 + ikd-Tree 甩掉了提特征、并让地图能一边长一边查，解决了「管得住」；Faster-LIO 用体素哈希把查询的代价从「随全图点数增长」变成「只看身边那一圈」，解决了「查得快、还能并行」。三篇的共同主线，是「不提特征 + 增量数据结构 + 更细的更新粒度」。

而它们共同的、没有被解决的边界，就是上一节点名的那件事：环境本身不给几何约束时，谁都无能为力。接下来这个模块剩下的几篇——Point-LIO（把更新粒度打到逐点、解决 IMU 饱和）、iG-LIO（把 GICP 的分布配准搬进来）、LOG-LIO（把法向与分布做成实时一等公民）——都是在这条主线的不同位置上继续加码。下一节我们先看 Point-LIO 怎么把「帧」这个概念本身拆掉。

课后练习

  1. Faster-LIO 是针对 FAST-LIO2 的哪个环节动刀的？原文说树结构有哪两个固有弱点？
    展开查看答案

    动刀的环节：地图（空间索引）的数据结构——把 ikd-Tree 换成 iVox 增量稀疏体素哈希。原文的说法是「we show that iVox is even faster than the ik-d tree in FastLIO2 while accomplishing the same level of accuracy」。

    树的两个弱点：

    ① 查询要顺指针一层层走：查询复杂度随全图点数按 $\log n$ 增长，树越大越慢。原文的表述是它不使用「complicated tree-based structures to divide the spatial point cloud」。

    ② 难并行：路径是串行依赖的——不走到这一层就不知道下一层往哪走，无法把一次查询拆给多个核心。因此原文用「parallel k-NN search」作为核心卖点之一，并把 FAST-LIO2 里的 OpenMP 换成了 libtbb + C++17。

  2. 请用「切块、哈希、每格限量」三句话解释 iVox，并写出它的哈希函数。
    展开查看答案

    三句话：① 切块——把世界按固定边长 $s$ 切成小立方格（体素）；② 哈希——体素坐标不直接当下标，而是通过哈希函数映射到哈希表的槽位，只为「真的有点的格子」分配空间；③ 每格限量——每个体素内只保留有限数量的点（插入时做了下采样），使格内搜索的规模可控。

    哈希函数：$id_v = \text{hash}(\mathbf{v}) = (v_x n_x)\ \mathrm{xor}\ (v_y n_y)\ \mathrm{xor}\ (v_z n_z)\ \bmod N$，其中 $\mathbf{v} = \frac{1}{s}[p_x,p_y,p_z]^{\top}$ 是体素坐标，$n_x,n_y,n_z$ 是大素数，$N$ 是哈希表容量。

    查询三步：① 算出查询点所在体素并找出邻近体素（6 / 18 / 26 邻格）；② 在每个候选体素里最多取 K 个近邻；③ 合并各体素结果，挑出最好的 K 个。

  3. 把 iVox 与第二季 0034 的 Voxel Hashing、第三季 0038 的 Instant NGP 放在一起，它们的共同招式是什么？iVox 与它们最关键的不同又是什么？
    展开查看答案

    共同招式：都是用哈希函数把「三维坐标」直接映射成一个内存地址 / 特征索引，从而绕开树状结构「一层层找」的过程。原文自己也点出了这个传承：「voxel hashing is also a common approach to replacing hierarchical tree-like structures」，并引用了在视觉 SLAM 与体积式重建中的先例。

    关键不同：格子里装什么、格子有多满。

    第二季 0034 的格子装的是 TSDF 值（稠密的截断符号距离场，用于表面重建）；第三季 0038 的格子装的是可学习的特征向量（用于神经辐射场）；本节 iVox 的格子装的是原始激光点。

    更要紧的是稀疏性：原文特意说明「Since the lidar point cloud is sparse, we are not using any volumetric representations like TSDF but a sparse hash map that only stores those voxels having at least one point」——激光点云极端稀疏，绝大多数格子里什么都没有，所以必须用稀疏哈希表，而不能用稠密的体积表示。这是激光这个战场与另外两个战场最大的区别。

  4. 论文里的「1000–2000 Hz」到底是什么口径？为什么不能说「Faster-LIO 以 1000 Hz 输出位姿」？
    展开查看答案

    口径：它是整套 LIO 流程的处理帧率（吞吐率），也就是「每秒能处理多少帧激光扫描」。原文在实验部分把 Hz 与 FPS 换着用，明确写的是「the average frames per second (FPS)」。

    而且原文三处表述并不完全一致：摘要写「1000–2000 Hz per scan」（固态）与「over 200 Hz」（32 线旋转式）；贡献列表写「over 1500 Hz」（固态）；结论写「over 1000 Hz」（固态）。这几个数字有出入，应当照实全部列出，而不是挑最大的一个用。

    为什么不能说「以 1000 Hz 输出位姿」：位姿输出率受 IMU 频率与扫描结构约束，和「数据处理能力的天花板」是两件事。把带宽明确推到 4–8 kHz 的是下一节的 Point-LIO，而 Faster-LIO 这篇并没有做这件事。同样也不能说成「激光雷达每秒吐 1000 个点」，那是把处理帧率错当成了传感器点频。

  5. iVox 路线有哪些已知的取舍与局限？其中哪一条是它「继承了 FAST-LIO2 而没有解决」的？
    展开查看答案

    ① 近邻不严格：原文亲口承认 iVox 的 k-NN「not strict compared with tree-like algorithms, yet sufficient for LIO applications」——是主动用精度换速度。

    ② 分辨率敏感：体素边长 $s$ 同时影响精度与速度（原文称 leaf size 是「the key parameter that tunes the trade-off between accuracy and speed」，经验值 0.5 m）；要更高的召回率就得把体素调大或把邻域范围开大。

    ③ 哈希冲突：不同体素可能映射到同一槽位，这是哈希类方法的固有结构性问题。

    继承而未解决的那一条：退化场景。FAST-LIO2 在原文中明确承认，在完全退化的环境（正对开阔海面、天空、纯地面、单一墙面、距墙不足 1 m）会失败。Faster-LIO 换掉的是地图数据结构，并没有改观测模型，所以这条边界原样继承。换句话说：换数据结构能解决「算得快不快」，解决不了「算不算得出来」。
